# 2026-05-06 — cyim-lsp Security Audit (v1.0.0 — API freeze)

First-pass security audit, paired with external CVE corpus
research. Walks the
[CLAUDE.md security-hardening checklist](../../CLAUDE.md)
inherited from cyim's first-party process.

**Predecessor:** _(none — first audit)_

**Goal:** identify CRITICAL / HIGH findings before v1.0.0 ships
the API-frozen plugin distfile to cyim 1.4.0. Triage anything
LOW.

---

## Methodology

Two-pass review:

1. **Internal review** — walk every public `lsp_*` function
   reachable from cyim's plugin-init hooks, every `var buf[N]`,
   every syscall site, every untrusted-input parser path
   (JSON-RPC framing, JSON walker, URI extraction, integer
   parses).
2. **External corpus mapping** — survey 2025-era LSP / JSON
   parser CVE classes; verify cyim-lsp's defense (refused-
   by-design / closed / open) against each.

Coverage cross-checks:

- [`tests/jsonrpc.tcyr`](../../tests/jsonrpc.tcyr) — 21
  framing assertions
- [`tests/subprocess.tcyr`](../../tests/subprocess.tcyr) — 15
  pipe / fork / exec invariants
- [`tests/lsp_diags.tcyr`](../../tests/lsp_diags.tcyr) — 43
  per-URI diagnostic state invariants
- [`tests/lsp_documents.tcyr`](../../tests/lsp_documents.tcyr)
  — 39 didChange / didSave / nav invariants
- [`tests/lsp_position.tcyr`](../../tests/lsp_position.tcyr)
  — 38 position / URI / coord invariants
- [`fuzz/jsonrpc.fcyr`](../../fuzz/jsonrpc.fcyr) — 5K random
  bytes through `jsonrpc_parse_frame`

## Threat model recap

cyim-lsp embeds in cyim under cyim's "trusted single user, not
a privilege boundary" trust model
([cyim ADR 0001](https://github.com/MacCracken/cyim/blob/main/docs/adr/0001-trust-model.md))
**plus** one addition: the LSP server's stdout — JSON-RPC
frames containing diagnostic / range / message data — is
**untrusted**. The server binary path is config (trusted), but
the bytes it streams back may have been derived from
attacker-controlled source files the server is processing.

See [`SECURITY.md`](../../SECURITY.md) for the formal threat
model; this audit verifies the implementation against it.

## Checklist coverage

### 1. Input validation

| Surface | Status | Notes |
|---------|--------|-------|
| JSON-RPC frame Content-Length header | **F-1** | Integer parse lacks overflow cap; see findings. |
| JSON-RPC body framing (`\r\n\r\n` boundary) | CLEAN | Strict prefix match; rejects unknown headers (`Content-Type` etc.) — stricter than spec but acceptable for cyim-lsp's single-server posture. |
| JSON walker (`_lsp_diags_walk_array`) | CLEAN | Brace-depth + string-aware; escape-state tracked. v0.5.1 fixed the depth-0→1 double-count regression. |

| URI extraction | CLEAN | Bounded by closing-quote scan + `blen`; LSP spec disallows unescaped quotes in `file://` URIs. |
| LSP server binary path (config) | N/A | Trusted from cyim's config (threat model §). Never accepted off the wire. |

**Result:** 3 LOW findings (F-1, F-2, F-3). All defense-in-depth
under the current consumer set; not exploitable in v1.0.0 but
worth fixing in v1.0.x.

### 4. Pointer validation

All `load8` / `store8` / `load64` / `store64` sites reviewed:

- All `load8(ptr + offset)` reads in parsers bounded by an
  explicit `offset < blen` (or `<= blen - needle_len`) guard
  earlier in the same loop. Verified for: `_lsp_diags_find`,
  `_lsp_diags_walk_array` first pass, `_lsp_diag_parse_int`,
  `_lsp_diag_parse_string` first pass, `_lsp_diags_extract_uri`,
  `_lsp_pos_*`, `_lsp_path_to_uri`, `_lsp_path_is_cyr`,
  `jsonrpc_parse_frame`.
- `_lsp_diag_parse_string` second pass: relies on first pass
  having validated structure; with stable buf this is safe but
  the bound guard isn't explicit. **F-3 below.**
- All `store8(dst + i, ...)` writes into heap allocations sized
  by an explicit `alloc(N + 1)` where `N` was computed from a
  validated source-side count. No off-by-one observed.
- All struct field offsets (`+0`, `+8`, ..., `+40`) match their
  documented entry-layout comments (lsp_state.cyr:32B, lsp_diags
  entry:48B, subprocess proc handle:32B, diag tuple:24B). Spot-
  checked via test invariants.

**Result:** Clean.

### 5. No command injection

cyim-lsp does **not** call `sys_system`. Subprocess spawn uses
`sys_execve` with explicit argv built from trusted config:

- `lsp_proc_spawn(cmd, arg1, arg2)` — `cmd`, `arg1`, `arg2` are
  cstrings supplied by the plugin's hardcoded server registry
  (default: `cyrius-lsp` with no args). They never originate
  off the wire.
- argv array is NUL-terminated and built before exec; no
  shell metachar interpretation.
- envp: see 2026-05-07 amendment below.

**Result:** Refused by design (argv side). No command-injection finding.

> **2026-05-07 amendment (cyim-lsp 1.0.3):** the original audit
> classified empty-envp (`var envp[1]; store64(&envp, 0)`) as
> part of the "no command injection" defense. That conflated
> two distinct surfaces. **argv hygiene** is the command-injection
> defense (and remains unchanged): explicit argv array, no shell
> interpretation, trusted-config-only strings. **envp scope** is
> a separate concern — environment passthrough doesn't enable
> command injection, and empty envp had a real cost: it stripped
> `PATH` from the child, so `/usr/bin/env cyrius-lsp` (the
> `lsp_client_start_default()` invocation) silently failed in
> any real consumer environment. cyim-lsp 1.0.3 populates envp
> from `/proc/self/environ`. Per the cyim ADR 0001 trust model
> (single-user, not a privilege boundary) this is appropriate.

### 6. No path traversal

Path handling is restricted:

- `_lsp_path_to_uri(path)` — concatenates `file://` prefix to
  `path`; doesn't normalize. cyim provides the path; cyim's
  buffer-state is the trust source.
- `_lsp_path_is_cyr(path)` — extension check only; no path
  walking.
- URIs received from the server in `publishDiagnostics` are
  compared against cyim's open-buffer URI list; unknown URIs
  are dropped (no implicit file open).

**Result:** No path traversal surface — cyim-lsp doesn't open
files itself, only references files cyim has already opened.

## Findings

### F-1 — Content-Length integer overflow in `jsonrpc_parse_frame`

**Severity:** LOW (defense-in-depth — not exploitable in
current v1.0.0 consumer set, but contract-violating).

**Location:** [`src/jsonrpc.cyr:219`](../../src/jsonrpc.cyr)

```cyrius
n = n * 10 + (c - 48);
```

**Description:** The Content-Length header parser accumulates
decimal digits into a 64-bit signed int without overflow
detection. A malicious LSP server could send

```
Content-Length: 99999999999999999999\r\n\r\n<garbage>
```

The `n` value would overflow i64 and wrap to a negative value.
The subsequent guard `if (body_start + n > len) { return 0; }`
would then evaluate negative-arithmetic and could spuriously
return `1` with `body_len = <negative value>`.

**Why it's currently LOW (not exploitable downstream):**
Current consumers (`lsp_diags_handle_frame`,
`lsp_documents.cyr` handlers) call `_lsp_diags_find(body, blen,
0, needle)` whose loop is `while (i + nl <= blen)`. With
negative `blen`, the loop never executes — find returns -1 and
the frame is silently dropped. No OOB read happens.

But the parser's contract — "return 1 ⟹ caller sees a valid
`body_len ≥ 0`" — is violated. Any future consumer that doesn't
bounds-check `body_len < 0` could be exploited.

**Fix (proposed for v1.0.x):** cap `n` at 16 MB (matches the
`_lsp_recv_frame` buffer cap; anything larger is rejected
upstream anyway):

```cyrius
n = n * 10 + (c - 48);
if (n > 16777216) { return 0 - 1; }   # malformed
```

**Test plan:** add a `tests/jsonrpc.tcyr` case that feeds
`Content-Length: 99999999999999999999\r\n\r\n` and asserts
return `-1`.

### F-2 — `_lsp_diag_parse_int` unbounded integer parse

**Severity:** LOW (defense-in-depth).

**Location:** [`src/lsp_diags.cyr:260`](../../src/lsp_diags.cyr)

**Description:** Same `n = n * 10 + digit` pattern as F-1, used
for parsing `"line":N` and `"severity":N` fields out of
diagnostic JSON. A server sending `"line":99999999999999999999`
would overflow.

**Impact:** the line number gets `+1`'d (LSP 0-indexed → cyim
1-indexed) and stored in a diag tuple. Negative lines are
filtered/clamped by cyim's render layer, so this doesn't
escalate. But same contract issue as F-1.

**Fix (proposed for v1.0.x):** cap at 100M (LSP coords are non-
negative; 100M covers any conceivable file).

---

### F-3 — `_lsp_diag_parse_string` second pass lacks `rp >= blen` guard

**Severity:** LOW (defense-in-depth).

**Location:** [`src/lsp_diags.cyr:317-345`](../../src/lsp_diags.cyr)

**Description:** The string parser is two-pass: first measures
the decoded length, second copies. The first pass has
`if (p >= blen) { return 0; }` at the top of its loop. The
second pass has no such guard — it relies on the first pass
having found a closing quote, so the second pass walks the
same bytes and stops at the same quote.

With stable input bytes, this is safe. But the contract isn't
defensive — if `body_len` were ever decremented between passes
(it isn't), or if there's a future race we haven't anticipated,
the second pass could OOB-read.

**Fix (proposed for v1.0.x):** mirror first pass's guard at
line 318:

```cyrius
go = 1;
while (go == 1) {
    if (rp >= blen) { return 0; }      # mirror first-pass bound
    var c = load8(body + rp);
    ...
}
```
